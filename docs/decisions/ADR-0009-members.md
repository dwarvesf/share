# ADR-0009: members serve from their own machines behind the tenant hostname, through Workers VPC

Status: proposed
Date: 2026-11-13

## Context

A tenant is one hostname with one origin machine (ADR-0008). Teammates publish cloud links only, each with a bucket-scoped token the admin makes by hand in the dashboard (ADR-0007). The owner wants a teammate's file to stay on that teammate's machine under the same hostname, no subdomain per member, no dashboard visit for the member, and a member lifecycle (add, pause, rotate, remove) with no half states. The design is `docs/briefs/DECISION-BRIEF-multi-member.md` (r2), reviewed adversarially in `docs/research/2026-11-13-multi-member-review-1.md` (3 blockers, 14 majors, all folded); the build is `docs/specs/SPEC-009-multi-member.md`.

Measured before this decision (`docs/research/2026-11-13-multi-member-spikes.md`, Console Labs, Workers Free plan):

- O1: a Worker reached a plain-HTTP server on `127.0.0.1` through a Workers VPC Service on a tunnel whose configuration holds only the `http_status:404` catch-all (no public hostname, no DNS record, no `warp-routing`). The origin saw `Host` equal to the fetch URL's host, path and query intact, and every request header unchanged, a test `cf-access-jwt-assertion` included. Bodies streamed (first byte 0.49 s). Added latency 151 to 354 ms. WebSocket was not tested.
- O2: a user token holding API Tokens Read and Write minted a token (200), the secret appeared only in the mint response, `PUT /user/tokens/<id>` moved `expires_on` in place with the secret unchanged, and the list found the token by name. Account-owned token endpoints answered 403 with every stored token.

Documented, not measured (`docs/research/2026-11-13-multi-member-outside.md`): Workers VPC is beta ("features and APIs may change"), free on every plan during the beta, 1,000 VPC Services per account; no API rotates a tunnel token (dashboard only), and running connectors survive a rotation until restarted; deleting a tunnel's connections force-disconnects them.

## Decision

- **Members serve from their own machines behind the one tenant hostname, through Workers VPC.** Each machine member runs its own Caddy and cloudflared on its own tunnel `share-<host>-<8hex>`, which has no hostname, no DNS record and no ingress rule beyond the required catch-all. One VPC Service per member tunnel targets `127.0.0.1:<port>` over plain HTTP, and the tenant Worker binds it as `M_<8hex>`. A member link is a v:3 pointer `m/<id>` naming its `origin` (the member_id); the Worker rewrites the request to `http://<HOST><path>` and fetches it through that binding. Origin links (v:2) and cloud links (v:1) route exactly as before.
- **The deploy is authoritative; the registry is a journal.** Routing lives only in the Worker deploy: the set of `M_<8hex>` bindings and the `PAUSED` list. Only the admin token can deploy. Every deploy, on every path (member verbs, `setup --r2` reruns, alias folds, version bumps), reads the deployed settings, carries every binding and `PAUSED` forward, and applies only the running verb's change. The bucket registry (`u/<member_id>.json`) records names, object ids, token ids and timestamps for humans and for reruns; it never feeds routing. `member ls` reports drift between registry and deploy; `member sync` repairs records from the deploy. After a deploy is wiped, the account's VPC Services (objects only an admin can create) are the rebuild source, never the records.
- **Every admin verb is resumable and serialized.** It holds a bucket lease (`lock/admin`, `If-None-Match`, staleness judged by the server's `LastModified`), writes `status=<verb>ing` before its first Cloudflare change, finds every object it may have made by a deterministic name, and converges on rerun.
- **Tombstones never delete bytes.** When someone other than the owner removes a machine link (the admin's revoke, or `member rm`), they write `t/<id>` and delete the pointer, so the link answers 404 at once. The owner's own reconcile marks its row revoked, stops serving it and deletes the tombstone. Bytes leave a machine only through that machine's own `rm`, the expiry of its own row, `leave`, or `leave --local`. Caddy serves listed, unexpired, unrevoked rows only, so a forged pointer cannot re-serve a revoked or unlisted file.
- **The trust limit stays ADR-0007's.** A bucket-scoped token cannot tell members apart: any publisher can write any key, `u/`, `m/`, `t/` and the marker included. This design does not close that; it bounds the worst case to visible and recoverable outcomes: a forged tombstone revokes a link the owner sees and can re-add; a forged pointer reaches only rows the target machine lists; a forged record changes no routing; a forged invite fails its MAC. Members are therefore named teammates only. Worker-mediated writes with per-member tool keys (plan B) are the upgrade before anyone outside the team publishes.
- **The Worker gains one narrow write, for redeem.** `POST /_share/redeem` with `h = sha256("share-invite-id:" + code)` touches only keys matching `i/<64 hex>`: it claims the object with a conditional overwrite (`onlyIf.etagMatches`) so two concurrent redeems cannot both win, deletes it, and only then returns the envelope; an expired envelope is deleted and answers 410. The Worker never decrypts and never writes any other key. The invite code (100 bits) never leaves the member's machine; the envelope is sealed with a key derived from the code (PBKDF2-SHA256, AES-256-CBC, HMAC-SHA256 encrypt then MAC).
- **Member tokens are minted by the tool, user-owned, with a separate minter token.** A minter token holding only API Tokens Read and Write, read from `SHARE_MINTER_TOKEN`, else from the output of the profile config key `minter_token_cmd`, and never stored by share (a separate 1Password item from the admin token), mints each member's publisher token (R2 bucket item write on the share bucket plus Zone Read, with an expiry), extends its expiry in place, and deletes it. The everyday admin token never gains the power to mint tokens. Member tokens are owned by the minting user and die if that user leaves the account; account-owned tokens are the upgrade once a token with Account API Tokens Write exists.
- **Same-origin risk across members, re-decided.** Every member's HTML now runs on the tenant origin, beside the origin's and every other member's links, some of them gated. ADR-0007 accepted one origin because only named teammates publish; tool-minted invites lower the effort to add one, so this ADR keeps the named-teammate rule explicit and adds two mitigations in the Worker: it strips `cf-access-jwt-assertion`, `cf-access-authenticated-user-email` and the `CF_Authorization` cookie before any binding fetch (the binding forwards headers unchanged, O1), and it adds `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups allow-downloads` (no `allow-same-origin`) to member answers of type HTML or SVG, so a member's page runs in an opaque origin and cannot read other links with the visitor's credentials. PDFs and other types are untouched. Per-member subdomains remain the isolation upgrade if an untrusted publisher is ever added.
- **The admin token comes from the environment or a configured command** (amended 2026-11-14, Share Bar interactions gap G3; SPEC-010 G13). Admin verbs read `CLOUDFLARE_API_TOKEN` first, else run the profile's `admin_token_cmd` (a command such as `op read op://<vault>/<item>/credential`, never the token, the pattern `api_token_cmd` already uses). With neither, the Share Bar asks for the token per action, passes it to that one command in its environment, and never stores it. Only admin paths run the command; listings, `state`, `status` and publisher paths never do. Before this, the admin token was environment only, so the Share Bar, which launchd starts with no shell environment, could run no admin verb. The minter token follows the same rule (amended 2026-11-14, owner decision on SPEC-009 OQ-8; SPEC-010 G13): `SHARE_MINTER_TOKEN` first, else the profile's `minter_token_cmd`, run once per process, never stored, and only on the minter paths (member add, invite, rotate, renew, rm, adopt). As built (SPEC-010 G13): `share admin-token --cmd|--clear|--test` and `share minter-token --cmd|--clear|--test` write or drop the key and probe the token's reach; the resolved token stays in the resolving process (never exported), and the serve daemon a setup starts runs under `env -u` for both variables.
- **Teardown of a tenant with members is refused** with the stable code `members_present` (gap G6) until every member is removed; `--no-members` then teardown is the way out.
- **Workers VPC beta is accepted behind `--members`.** A tenant turns members on with `setup <host> --r2 --bucket <b> --members` (T1 to T2) and off with `--no-members` once every member is removed. Without the flag nothing in this ADR touches a tenant. If Workers VPC regresses, the credential half (minted tokens, redeem-once invites, cloud members) needs no VPC object and stays.
- A member's tunnel belongs to the tenant account, so an account admin with Connectivity Directory Admin could bind further services to it and reach whatever the member's machine reaches. `join` says so, and recommends a dedicated user or a host firewall; `member ls` lists every VPC Service on each member tunnel.
- `rotate` replaces a member's tunnel and VPC Service and rebinds the same `M_<8hex>`, because no API rotates a tunnel token; a leaked connector stops when its tunnel is deleted.

Alternatives rejected:

- One tunnel with many connectors: Cloudflare spreads requests across a tunnel's connectors, so links fail at random.
- A hidden origin hostname per member behind an Access service token: a real DNS name and a secret per member; the owner asked for no new subdomain.
- A routing table in the bucket read per request: one more R2 read per request, and every publisher can write it.
- The deploy rebuilt from registry records: a paused member could rewrite its own record and be unpaused by the admin's next deploy (review-1 finding 5).
- Destructive tombstones (the owner deletes bytes on a tombstone): any token holder could delete files on every machine (review-1 finding 1).
- An invite blob with raw tokens sent over chat or 1Password: it stays valid forever, and the connector token inside never expires (review-1 finding 6).
- Granting API Tokens Write to the admin token: a leaked admin token would mint itself any permission its user holds (review-1 finding 15).
- Plan B now (the Worker accepts publisher writes with tool keys): a write path and R2 write credentials inside the Worker, not needed while publishers are named teammates.
- `PATCH` of a tunnel secret to rotate a connector token: undocumented.

## Consequences

- A teammate shares a file that never leaves their machine, at `https://<tenant host>/<id>/`, and joins from one pasted line without opening the dashboard.
- Every member change redeploys the whole Worker; a verb waits until `/healthz` echoes its deploy nonce three times before it returns. The binding count per Worker is undocumented, so the CLI caps machine members at 20 until it is measured.
- Member links add 150 to 350 ms per request and answer a generic 503 offline page while the member's machine is off; origin and cloud links are unaffected.
- A forged or careless bucket write by any publisher can still revoke a member link or rewrite a registry record. Both are visible (`ls`, `member ls`) and recoverable; neither deletes bytes or changes routing.
- A removed member's cloud links keep serving until they expire unless the admin asks for their deletion.
- Members cannot add gated links, live port shares (until WebSocket through a binding is proven), or `--host` links, and do not get hit counts.
- An older share (v0.9) on a T2 tenant never sees, reaps, or mis-serves a member link, but its orphan upload sweep skips while v:3 records exist; the marker's `min_cli` binds every CLI from v0.10 on, and the owner confirms every publisher has upgraded when turning members on. An older CLI that downgrades the Worker with `--force` drops every member route until `member sync --rebind`.
- Workers VPC is beta: a Cloudflare change can break member routing without a share release. Members are opt-in per tenant, and `--no-members` is the rollback.
- Member tokens depend on the minting user's account membership.
