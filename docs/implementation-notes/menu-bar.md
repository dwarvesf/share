# Implementation notes: menu bar app

Delta from `docs/specs/SPEC-003-menu-bar.md`. Decisions already in the spec are referenced, never restated.

## Decisions made without the operator

- The operator delegated the whole cycle and was away, so design and spec approval were self-approved and recorded in the gate ledger as such. The design lane's one-question loop could not run (bypass mode).
- Research changed the contract before it was written: no `version` field (the script carries no version string), a `serves_here` field added (the `hosts=` guard), `SHARE_CLIPBOARD=0` set for every child process.

## Deviations

- The first spec draft used `share status --json`. The design review showed an older CLI ignores the flag and prunes, so the contract became the verb `share state` (DEC-008). The ADR carries an amendment line rather than a rewrite.
- The review turned up two bugs in share that exist today and that the app would trigger more often: concurrent index writers lose rows, and `quick.url` survives `stop`. Both are fixed in the spec's TASK-001 instead of a separate PR, since the app's correctness depends on them.

## Landmines found while building

- bash 3.2's `printf '%d' "'c"` sign-extends bytes above 127 (`%FFFFFFFFFFFFFFC3` for the first byte of `é`). The pure-bash `urlenc` masks with `$((c & 255))`; probed against `jq @uri` on accented, CJK and emoji names under both `/bin/bash` 3.2 and bash 5.

## Open questions for the operator

- The final product name. The spec ships "Share Bar" as a working name (DEC-007); the rename touches one constant, the Info.plist, and the cask file.

## 2026-09-27 15:00 TASK-006: ShareBarCore CLI runner

- Used `posix_spawn` directly (not Foundation's `Process`), since `Process.terminate()` only signals the direct child and the spec needs `killpg` to reach grandchildren (e.g. a `sleep 30 &` a shell wrapper backgrounds).
- `SHARE_BIN` is trusted outright when set, no `fileExists` check, matching the existing convention for `SHARE_ROOT`/`SHARE_CONFIG_DIR` in `bin/share` (both are trusted env overrides with no existence probe). The four fixed candidate paths are each gated by the injected `fileExists`, since those are guesses, not explicit operator intent. The spec's acceptance line ("locate order with an injected file-exists check") doesn't pin down whether `SHARE_BIN` itself is checked; this reads it as consistent with the bash side's convention.
- The exit-status decoding for the BSD wait status is a plain reimplementation of `WIFEXITED`/`WEXITSTATUS` (the C macros aren't directly callable from Swift): normal exit yields the exit code; a signal-killed process yields `128 + signal`, the common shell convention. Not stated in the spec; only `status: Int32` is.
- `MutationQueue` chains each call onto the previous call's `Task` rather than relying on actor isolation alone: a bare `await CLI.run(...)` inside an actor method is reentrant (Swift actors interleave suspended calls), so two `run()` calls could otherwise spawn concurrently despite the actor. Verified with a negative control (reverting to the bare/reentrant form fails the strict-order test, "B\nA\n" instead of "A\nB\n").
- The shared in-flight `state` call is a private `StateCoalescer` actor behind `CLI.state(timeout:)`, not a new type in the public API sketch; `CLI`, `CLIResult`, and `MutationQueue` are the only names the spec pins. Verified with a negative control (dropping the coalescing spawns 3 processes for 3 concurrent calls instead of 1).
- `CLI.spawnCancellable` and `CLIJob` are implemented per the API sketch (streaming `onOutput`, `cancel()` TERMs the group then KILLs 3s later) even though TASK-006's acceptance bullets don't name a specific test for them; TASK-011 (the setup window) is the real consumer. Added one smoke test covering streaming + cancel-kills-the-group, using the same `/bin/sh -c 'sleep 30 & echo $!; wait'` shape as the timeout test.

## 2026-09-27 12:31 Locks: prune loop rewritten for bash 5.3 EXIT traps

- Context: the spec relies on `lock_take` re-arming `trap release_locks EXIT` inside subshells. The new "die inside prune's pipeline" test failed under brew bash 5.3.20 and passed under `/bin/bash` 3.2.
- Decision/Change: `cmd_prune` collects expired ids with `ids="$(awk ...)"` and loops with `for id in $ids`. The old code piped awk into `while read`. `cmd_rm "$id" | sed` stays a pipeline.
- Why: bash 5.3 skips an EXIT trap set inside a `| while` body subshell, including a pipeline nested in it. A plain `cmd | sed` pipeline child runs its trap in both shells (probed).
- Alternatives: a `BASH_SUBSHELL`-aware release in the parent. Rejected: more code, and the parent cannot know which lock a dead child left.
- Impact: ids are 6-hex, so word splitting is safe. The prune test runs under both `bash` and `/bin/bash`.
- Open questions: none.

## 2026-09-27 12:31 Locks: details the spec left open

- Context: the spec pins pid symlinks and rename-then-check. It leaves the timeouts, the release rule, and the upgrade case open.
- Decision/Change: `lock_take <name> [secs]` defaults to 60s. `host_lock` passes `SHARE_HOST_LOCK_TIMEOUT` so the existing knob keeps working. `index` has no knob. `held_locks` holds lock names, not paths, so a `$root` with spaces survives word splitting. `lock_release` removes the link only when its target is still `$$`. A real directory at `.lock-<name>` counts as held.
- Why: `ln -sn pid dir` creates a link inside an existing directory and succeeds, so a leftover pre-upgrade `mkdir` lock would silently disable locking. Treating it as held keeps today's behavior: time out and name the lock.
- Alternatives: `rmdir` a legacy directory automatically. Rejected: it cannot tell a leaked lock from one an old binary holds.
- Impact: residual window in the stale rule. A waiter moves a live link back with `mv -f`. A third process that took the lock during that window gets overwritten. Two waiters must both read a dead pid first, so this needs three racing processes. Accepted.
- Open questions: none.

## 2026-09-27 12:31 Test: the Caddyfile negative control needed a forced interleaving

- Context: negative control 4 (render after releasing `index_lock`) passed the first parallel test in every run. `write_caddyfile` now renders to `mktemp` and moves the file in, so an unlocked render is always whole. Stale only happens when an older render lands last, and renders finish in start order.
- Decision/Change: the test seeds 60 inert rows to stretch each render to about 100ms. It freezes the first remover (SIGSTOP) 50ms after its row leaves the index. If the frozen process holds `.lock-index`, the test resumes it after 0.3s. If not, it stays frozen until the other writers finish. The padding rows go away after the section.
- Why: random SIGSTOP jitter caught the control in 25 to 75% of rounds. The targeted freeze caught it 12/12 in a harness and 5 of 6 suite rounds. The real code stayed clean 12/12.
- Alternatives: a sleep seam inside `write_caddyfile`. Rejected: a test hook in production code.
- Impact: suite time stays about 30s. Negative control 2 (no lock in `cmd_rm`) fails both rounds.
- Open questions: `refresh` racing `rm` on the same id can recreate `pub/<id>` after the row is gone. The payload stays served with no row. This behavior predates the change and is out of scope here.

## 2026-09-27 17:20 TASK-016: small CLI hardening

- `rand_id`'s collision loop needs an injectable id source for the acceptance test ("a stubbed id source returning a taken id twice, add gets a third id"). The spec left the injection mechanism open ("your choice, logged"). Chose an env-var seam over a function-override hook: `rand_id_raw()` (the actual `od`/urandom draw) checks `SHARE_TEST_IDS` first and, if set, consumes and returns its next space-separated token instead of drawing random bytes. `rand_id()` itself just loops calling `rand_id_raw` until the candidate is neither an existing row nor an orphaned `pub/<id>`. A function-override hook was rejected: bin/share is always run as a fresh `bash "$0"` subprocess per test invocation, and the script unconditionally redefines every function at parse time, so a parent shell's exported function of the same name is silently shadowed the moment the script loads. An env var survives that.
- `cmd_rm`'s new no-credential refusal is gated on `${SHARE_HOST_DRY:-0} != 1`, matching the existing gate in `host_check`/`host_add`/`host_rm`. Not spelled out in the hardening bullet itself, but required for consistency: without it, every existing dry-mode own-host `rm` test in the suite (which never sets `CLOUDFLARE_API_TOKEN` and never creates `cert.pem`) would start failing, since dry mode is the suite's stand-in for a real credential rather than an absence of one.
- `cmd_rm` takes an optional second arg (`prune`) so `cmd_prune`'s loop can opt out of the new refusal (DEC-016); the refusal itself checks `${2:-} != prune`. `host_rm` already had its own no-credential warn-and-continue branch for the non-dry path, so prune's behavior needed no other change.
- The "malformed row" bullet (skip rows with fewer than 5 or more than 6 tab fields) is applied to every raw index-reading site the hardening bullet names outside `state` (which doesn't exist yet): `row()`, `cmd_ls`, `cmd_prune`'s awk id-selection, both `write_caddyfile` loops, and `id_of`'s host-match awk. Each now filters on `NF==5||NF==6` (via awk) before use; a 5-field legacy row still passes through with `opts` reading empty, matching `read`'s existing tolerance for a missing trailing field.
- The tab/newline basename check sits right after `name="$(basename "$src")"` in `cmd_add`'s snapshot branch, before any write (mkdir, copy, host_check/host_zone's config append, or rand_id draw). Live shares never reach this branch, since their "name" is a synthesized `localhost:<port>` string that can't contain either character.

## 2026-09-27 13:26 refresh-vs-rm publish leak (found by the TASK-001 verification)

- Context: `cmd_refresh`'s `copy()` runs outside the index lock and ends with `mv "$stage" "$pub/$2"`. A parallel `rm` of the same id trashed `pub/<id>` and dropped the row before that `mv` landed, so the refresh's own copy republished the directory after `rm` had already printed "unpublished". `prune` never caught it, since it walks index rows only, and the main site block's catch-all `file_server` over `$pub` then served the recreated directory publicly.
- Decision/Change: `cmd_rm` now trashes `pub/<id>` only after the index rewrite, inside the `index` lock. `cmd_refresh` rechecks the row right after taking the `index` lock; if the row is gone it trashes `pub/<id>` again (covering the copy that already landed) and dies naming the id, instead of trusting the mv.
- Why: both writers already serialize on the same `index` lock (TASK-001); moving each side's `pub/<id>` write inside that lock removes the race window instead of narrowing it.
- Verified with a negative control: reverting both orderings makes `tests/share.sh`'s new "refresh racing rm" check fail (`pub/<id>` survives after `rm` reports success, 170 ok + 1 FAIL); restoring the fix turns the whole suite green again (171/171).

## 2026-09-27 13:45 TASK-007: ShareBarCore model (Snapshot decode, MenuModel rules)

- `Failure` (`Sources/ShareBarCore/Snapshot.swift`) is a 3-case enum, not the four the task brief names, because "undecodable output" and "any other failure" are the same bucket: both fall through to `.other(String)`, carrying the header line already composed (`share: <last non-empty stderr line>`, or `share exited <n>` when stderr is empty). `.cliNotFound` and `.oldCLI` are the only cases with their own fixed header text, so they get their own cases; everything else shares one. `Failure` conforms to `Error` (needed for `Result<Snapshot, Failure>` to compile) and `Equatable` (needed for the mapping tests).
- Old-CLI detection matches the task brief's instruction over the main spec paragraph's wording: `result.status == 1 && result.stdout.hasPrefix("share: publish snapshots")`, the literal first line `bin/share`'s unknown-verb branch prints (`sed -n '2,17p' "$0" | sed 's/^# \{0,1\}//'`, stdout, exit 1), read straight from the script rather than assumed.
- "Any other failure" header composition follows the main spec paragraph literally ("`share: ` plus the last stderr line") over a looser reading that would treat an already-`die()`-prefixed stderr line as the whole message: the code always prepends `share: `. This only double-prefixes for a `die()`-originated line, and `state`'s own failures (its likely source: a missing `jq`, a bash syntax error) are raw shell errors with no such prefix, so the double-prefix case does not arise in practice. Flagging the reading in case TASK-005's real `cmd_state` failure paths turn out to route through `die()`.
- `CLI not found` detection matches the exact sentinel string `CLI.run`/`CLI.spawnCancellable` already return when `locate` fails (`stderr == "share: CLI not found"`), not a status-code guess, since 127 is also `env`'s and bash's generic "not found" exit code and could otherwise collide with an unrelated real-CLI failure.
- `Icon` is a two-case enum (`connected`/`disconnected`) rather than carrying an SF Symbol name string, since naming the symbol is AppKit's job (out of scope here); the model only needs to say which of the two states applies (serving && ready).
- `showStart`/`showSetUp`/`icon` all default to `false`/`false`/`.disconnected` when there is no snapshot (a `Failure`-only `MenuModel`), since the spec defines those three only in terms of snapshot fields and a failed read has none.
- The header precedence chain is written as an ordered `if`/`guard` chain, not a `switch` on `state`, because two of the rules ("Not set up" and "Not serving on this Mac") can both be true of the same snapshot (`state == "not_setup"` with `serves_here == false`) and the spec's ordering, not the state's own semantics, decides which wins; a state-keyed switch can't express that.
- `Tests/ShareBarCoreTests/Fixtures/state.json` is hand-written per the task's instruction (TASK-005 runs in parallel and `share state` does not exist yet): one snapshot share (`.md` rendered to `.html`), one live share, one own-host share, plus an unknown top-level field (`cloudflared_version`) to prove additive fields decode cleanly. Registered via `Package.swift`'s new `resources: [.copy("Fixtures/state.json")]` on the test target and read through `Bundle.module.url(forResource: "state", withExtension: "json")` (no `subdirectory:` argument: SwiftPM's `.copy` flattens the file into the bundle's `Resources/` root, it does not preserve the `Fixtures/` path inside the bundle).
- Per the task's forward-compat note, `SnapshotDecodeTests` asserts on the fixture's *shape* (one share of each required category, present, non-empty ids/urls) rather than on its specific ids, so the same assertions still hold once TASK-005's real CLI output replaces the file. `MenuModelHeaderTests` and `RowAndModelRulesTests` build their own synthetic `Snapshot`/`Share` values via `makeSnapshot`/`makeShare` test helpers instead of reading the fixture at all, since header/trailing-text/cap rules need specific boundary values (exactly 24h, exactly 60m, `expires == now`, 30 rows for the cap) the fixture was never meant to carry.

## 2026-09-27 TASK-003: pure-bash urlenc and fork-free share_url

- Context: the spec pins the byte loop itself (`LC_ALL=C`, the keep-set, the `& 255` mask) and the fork-free contract for both functions; it leaves the name of the result-holding global open.
- Decision/Change: `urlenc` sets `urlenc_out`; `share_url` sets `share_url_out`. `share_url` runs the whole `path` (which may contain `/`) through one `urlenc` call rather than encoding it segment by segment, since the byte loop already keeps `/` literal, the same effect as jq's per-segment `@uri` and rejoin. Every caller (`gen_index`, `cmd_add`, `cmd_ls`) now reads the matching global right after the call instead of capturing stdout.
- Why: no caller needs the result outside the calling scope, so one global per function is enough; the spec's own wording ("sets its result in a global") already fixed the shape, only the name was open.
- Alternatives: none considered.
- Impact: none behavioral. `cmd_ls` output is unchanged for every existing fixture (full suite green); a name with `#`, `?`, `%`, or non-ASCII bytes now links correctly instead of 404ing.
- Verified with a negative control: adding `#` to `urlenc`'s keep-set makes the new jq-vs-bash encoder comparison fail under both `bash` and `/bin/bash` (`urlenc(bash) [a#b?c%d&e+f=g]: want [a%23b%3Fc%25d%26e%2Bf%3Dg] got [a#b%3Fc%25d%26e%2Bf%3Dg]`); restoring the keep-set turns the suite green again (178 ok, 0 FAIL).
- Open questions: none.

## 2026-09-27 TASK-008: status item and menu rendering

- Context: the spec pins the model rules (`showStart`, `showSetUp`, `canCopy`, `canRefresh`, `removeText`, the 25-row cap) in `ShareBarCore`, and the update mechanism ("`NSMenuDelegate menuNeedsUpdate`/`menuWillOpen`, update items on the main queue in run loop common modes"). It leaves the Start/Stop toggle's exact source, the CLI-missing flag, and the row's two-column layout open.
- Decision/Change: added two small `MenuModel` fields, with unit tests, alongside the existing ones: `showStop` (`true` only when `snapshot.state == "serving"`) and `showCopyInstallCommand` (`true` only for `Failure.cliNotFound`). The mockup's single "Stop Sharing | Start Sharing" slot reads as `showStop ? "Stop Sharing" : (showStart ? "Start Sharing" : nil)`; without `showStop` the AppKit layer would have had to re-derive "is it serving" from the header string or duplicate the state check outside `ShareBarCore`, which the spec's own boundary ("logic belongs in `ShareBarCore`") argues against.
- Why: same reasoning applies to `showCopyInstallCommand`, since "CLI missing only" is a `Failure` case check, not something the view layer should re-derive by string-matching the header text.
- Alternatives: read `NSApp`-side state (header text prefix, or a raw `Failure?` passed to the controller) instead of adding model fields. Rejected: it re-implements a rule the model already computes from the same inputs, and duplicates the spec's precedence logic in two places.
- Impact: none behavioral; both fields are additive to `MenuModel`'s public init signature (unchanged). `RowAndModelRulesTests` gained `testShowStopIsTrueOnlyWhenServing` and `testShowCopyInstallCommandIsTrueOnlyWhenCLIIsNotFound`.
- Row titles (plain `NSMenuItem`, no custom view per the house rule) render as `"\(title)    \(trailing)"`, four spaces, no attributed-string columns; AppKit doesn't lay out a two-column menu item without a custom view, and the task rules out custom views.
- Copy Link, Open in Browser, Refresh, and Remove… are always present in every share's submenu (never omitted), each `isEnabled` toggled from the row's `canCopy`/`canRefresh` flags; the hits line is a permanently-disabled "Loading…" placeholder. This matches the task's literal wording ("items present and wired to no-op or disabled per model flags") over the mockup's "(snapshots only)" annotation, which reads as an explanation of when Refresh is enabled, not an instruction to hide it for non-snapshot rows.
- `menu.autoenablesItems = false` on both the main menu and every per-share submenu: AppKit's default auto-validation re-enables any item with a non-nil `target`/`action` pair regardless of an explicit `isEnabled = false`, which would have silently undone the canCopy/canRefresh gating.
- Chose `menuNeedsUpdate(_:)` over `menuWillOpen(_:)` as the single refresh trigger (the spec names both as acceptable): it fires once per open, before display, same as `menuWillOpen`, and is the one AppKit also calls for a live-tracking re-validation pass.
- The refresh completion hops back with `RunLoop.main.perform(inModes: [.common], block:)`, not `DispatchQueue.main.async`, taken literally from the spec's own wording ("on the main queue in run loop common modes"). `Task { await CLI.state() }` resumes on an arbitrary thread, and `RunLoop.perform(inModes:)` is the documented cross-thread-safe way to schedule a block onto a specific run loop in specific modes (`CFRunLoopPerformBlock` + wake, not thread-affine), which a plain GCD hop leaves implicit.
- `StatusItemController` is declared `@unchecked Sendable`: every mutable property is touched only from `init` (main thread) or from inside that same `RunLoop.main.perform` block, so the compiler's Sendable-closure-capture warning was a true negative, not a hidden race; documented inline rather than silenced with `@preconcurrency` or restructuring the closure to avoid capturing `self`.
- Open at Login renders its checkmark and "(approve in System Settings)" wording from a live `SMAppService.mainApp.status` read on every `applyModel()` call, ahead of TASK-009's actual registration/deep-link wiring, since reading status is non-mutating and the task's title is specifically "status item and menu RENDERING." The item's click action stays the shared no-op until TASK-009.
- Manual verification used `osascript`/System Events (`click menu bar item 1 of menu bar 1 of process "ShareBar"`, reading the item's `description` = the AppKit `accessibilityLabel`) plus `log stream`/`log show --predicate 'subsystem == "foundation.d.share.bar"'` instead of a visual screenshot for the live-update, poll, and stub-driven state-flip checks: this sandboxed session's `screencapture` returns an all-black image (Screen Recording TCC not granted to whatever process is invoking it here, and no Full Disk Access to inspect or fix `TCC.db`), and `orca computer get-app-state` fails with `permission_denied`/"no accessibility window" for both the target app and an unrelated control (`Finder`), i.e. a session-wide AX-read block despite `orca computer permissions` reporting "granted." Two independent screenshot paths failed for session-level reasons, not a bug in the app; `docs/verification/menu-bar-menu.png` is saved per the instructions but is not visual proof, only the AppleScript/log evidence below is.
- Wake refresh (`NSWorkspace.didWakeNotification`) is implemented and registered the same way as the poll timer and menu-open triggers, all three funnel into the same `triggerRefresh()` already proven live by the other two paths, but is itself **untested**: sleeping the real Mac was not attempted (a live, shared session, and putting it to sleep is a disruptive, not-easily-reversible action outside this task's scope), and a probe distributed-notification post (`DistributedNotificationCenter.default().postNotificationName("NSWorkspaceDidWakeNotification", ...)`) produced no reaction, meaning `NSWorkspace`'s wake notification is not simply a re-exposed Darwin/distributed notification of that name and can't be synthesized from outside the process. Per the task's own fallback ("if you cannot sleep the Mac ... say it is untested"), this is reported as untested rather than faked.
